# OITUI Development Notes

Hard-won technical constraints, safe patterns, and workflow lessons from OITUI development.

## Technical constraints

- **MobileGestalt writes are dangerous.** Writing `ArtworkDeviceSubType` without backing up the original caused a total homescreen/touch lockup that persisted through tweak removal. Always back up first, and restore via a compiled helper invoked from `prerm`. Do not use `CFPreferences` for this (its user-domain behavior is ambiguous in a root context).
- **A backup is only as good as when it was taken.** OITI once captured "original = 2556" while the spoof was already in the cache, so turning the Island off wrote the spoof back (a silent no-op) and uninstalling would have left it in place. Never record the spoof value as the original on hardware that does not natively report it (only the iPhone 14 Pro, `iPhone15,2`, does on iOS 16); record the original as absent so a restore removes the key and iOS recomputes it. Never capture a backup when the cache could not be read. Take a snapshot copy of the cache before any risky test.
- **Never write `.frame.origin` on pooled system views.** Direct frame-origin writes on system status bar views caused permanent teardown (`view.window == nil`). Transform-only repositioning is the safe pattern.
- **Apply corrections only from `CADisplayLink`.** Do not apply them from system-invoked callbacks such as `setFrame:` or `layoutSubviews`. Hooks may reset state and record natural positions; the tick reapplies.
- **Global Logos class hooks fire on every instance.** App Switcher, Control Center and the lock screen contain mirrored copies of hooked status bar views, so scoping guards are needed. The lock screen is architecturally unreachable by this approach.
- **Use flat plist files at explicit paths** for data that uninstall scripts must read. `CFPreferences` user-domain access is unreliable in a root context.
- **Keep Theos projects in the native Linux home directory** (for example `~/theos-projects`), not under WSL's `/mnt/c/`.

## Status bar internals (observed on iOS 16.7)

- **There are several `_UIStatusBar` instances at once.** The persistent one lives in `UIStatusBarWindow`; each app gets another inside an app-switcher page in `SBMainSwitcherWindow`; the cover sheet has its own. The inactive instance is hidden by fading its `UIStatusBar_Modern` ancestor to alpha 0, so "alpha 0 on an ancestor" is normal, not a bug.
- **Views are pooled and re-used.** The same view instance is detached and re-attached repeatedly, so transforms applied to a view persist across re-use. Anything that stops tracking a view must also reset it, and "forget on window loss" is not the same as "reset".
- **Slots can hold more than one view.** The time view and the carrier/network text view can share a slot and swap with a crossfade (alpha 0, scale 0.75), detaching the time view in between. Never identify the clock by "it's the only string view"; use its text (for example, a digit plus `:` or `.`).
- **Visual providers choose the layout.** A Split provider lays content out for a fixed reference width and stretches the foreground view with a uniform scale transform. Child frames are in pre-scale space, so convert desired on-screen offsets by dividing by the parent scale.
- **Third-party tweaks hook the same views.** Hook `setTransform:`, `setHidden:` and `setAlpha:`, flag your own writes, and log the call stack for everyone else's. The stack names the culprit dylib. This is how a separate landscape-status-bar tweak was found resetting the clock's transform every 150 ms.
- **The visual provider is chosen in `+[_UIStatusBarVisualProvider_iOS visualProviderSubclassForScreen:visualProviderInfo:]`** (returns a `Class`, takes the screen and an info dictionary, which was `nil` in every observed call). `_UIStatusBar` keeps `_visualProviderClass` and `_visualProviderInfo` and builds the provider in `-_prepareVisualProviderIfNeeded`. `+class`, `+_implementationClass` and `+_statusBarImplementationClass` do not choose it on iOS 16.7.
- **The provider family is keyed by native pixel width:** `Split828`, `Split1080`, `Split1080_Wide`, `Split1125`, `Split1170`, `Split1170_Wide`, `Split1242`, `Split1284`, `Split1284_Wide`, plus `DynamicSplit` and `DynamicSplitMedium` for Island hardware. A 13 mini natively gets `Split1080_Wide`. `_UIStatusBarVisualProvider_Fallback` is a separate placeholder class.
- **The red `rdar:45025538` bar comes from the spoof alone.** With `ArtworkDeviceSubType` 2556 on a screen UIKit does not expect, the selector returned `nil` (an iPhone 13 mini). The fix is to return the native provider while the Island is on, and to log what UIKit chose with the Island off.
- **`UIScreen` scale lies on minis:** an iPhone 13 mini reports bounds 375 x 812 with scale 3.0, but its native bounds are 1080 x 2340 (native scale 2.88). The old 360 x 780 table entry was wrong.

## Debugging and logging practice

- **Log state changes, not every tick.** Compare a compact signature per view and log only when it changes.
- **Rate-limit every log line** by key, and count what was dropped. A 60 Hz path can otherwise flood the log and stall the main thread.
- **Write logs asynchronously** on a private serial queue. Open, append and close per line so deleting the file while running just starts a fresh one. Rotate by size.
- **Give stack traces a per-event-type budget.** A single global budget was used up by one repetitive event before the interesting ones occurred.
- **Log a session header** with a build tag and PID on every start. More than one session in a file means SpringBoard restarted.
- **Add a visibility watchdog** that reports why a view is invisible (hidden or alpha on an ancestor, off-screen, no window) and auto-dumps the hierarchy the first few times.
- **Review state flags for dead code.** The `sPrevious*Enabled` flags in OITS were declared and read but never assigned, so reset-on-disable could never fire.
- **Full-tree window walks are not free.** A discovery walk across all windows every 10 ticks measured 2–4 ms; prefer targeted discovery from the foreground view.

See `DIAGNOSTICS.md` for the OITS tags, trigger file and commands.

## Phone shell and rootless pitfalls

- zsh on the phone does not treat `#` as a comment in interactive mode, so inline comments become arguments. Do not paste commands with trailing comments.
- Shell functions such as a `mark` helper must be defined in the phone's shell, not the Mac's.
- `/tmp` is sticky: files created by root over SSH cannot be replaced or deleted by `mobile` (SpringBoard). Detect trigger files by modification time rather than by deleting them.
- `find` does not follow symlinks, so tweak directories behind symlinks (for example `/var/jb/Library/MobileSubstrate/DynamicLibraries`) can be missed. List them directly.

## OITI internals (observed in code review)

- OITI works by spoofing `ArtworkDeviceSubType` (2556) so iOS builds Apple's real Dynamic Island, then repositions and restyles it. Any feature that needs its own Island content needs a separate mechanism.
- The original code had six copies of one device if/else chain, so lists drifted apart (the prefs "supported devices" list omitted the iPhone 12 family that the tweak handled). Keep one table and have everything read it.
- Calling `%orig` unconditionally at the top and again inside branches runs layout twice. Call it once.
- A hook that replaces `didMoveToWindow` without calling `%orig` skips Apple's own work. Always call it.
- Don't force `hidden = NO` on a system view when your feature is off. Track that you hid it, and only undo that.
- Defaults in code must match the globals and the prefs UI. Mismatched defaults (`alpha` 0.0 against 1.0, `yPos` 0.0 against 20.5) made features look broken until a slider was touched.
- Check `|` against `||`: `a && !b | a && !c` parses very differently from what it looks like.
- Use the clamped value consistently. The Island's Y divisor used the raw scale while the transform used the clamped one.
- Overriding a getter or setter for unknown devices must fall through to the original, not swallow it. `-setFrame:` used to be swallowed entirely on devices with no table entry.

- **Settings footers live in the card that follows their group (Nov 2026).** The custom Settings page (`oiti_buildSettingsPage`) turns each `PSGroupCell` into a header and puts its `footerText` at the bottom of the next card. A group directly followed by another group has no card, so its footer used to vanish (Scale > Island Size). The builder now looks ahead and shows such a footer under the header; `tools/check_settings.py` lists the cases.
- **One value, one job (Nov 2026).** The Opacity slider (`alpha`) used to feed both the custom color's alpha and the pass-through subview's alpha, so with both features on the fade was applied twice. The color is now always opaque; give a new setting its own key rather than reusing one for a second effect.

- **Typed position settings go through one strict parser (Nov 2026).** The Settings text fields used to store whatever was typed and OITCore parsed it with `-doubleValue`, so "" and "abc" became 0 and "nan" or "1e30" could reach a window frame. `OITI/OITIPositionValues.h` (`OITIParsePositionText`, `OITISanitizedPosition`, Foundation only) is shared by the tweak and the Settings bundle: plain number only, finite, limited to a ceiling of 1000 on load and to one screen at the point of use (`OITIPositionLimits.h`, UIKit). A bad stored value gives the setting's default, never 0. OITCore did not change.
- **A new customization must be forced off in Apple Mode at the same place (Nov 2026).** The notification haptic read its preference raw and ignored Apple Mode. Rule: read the preference into a global in `preferencesChanged`, force the global off in the Apple Mode block, and have the feature read the global (and the snapshot show the global).

- **Nothing on the %ctor path may touch UIKit singletons (bootloop, Nov 2026).** The %ctor calls `preferencesChanged()` before the loop guard is evaluated. v0.3.0 batch 1 added a `[UIScreen mainScreen]` call to it (a limit helper in `OITIPositionLimits.h`, reached through `OITIReadPositionPreference`), and the build `0.2.5-2+debug` left an iPhone 8 Plus stuck on the Apple logo; removing OITI fixed it. Evidence: the new object for `Shared/OITIPreferences.xm` referenced `UIScreen` and the v0.2.5 one did not; no other change to the launch path exists. No crash report was read, so the exact failure (crash or hang) was never confirmed; the fix build (`-c`) boots and works on the phone, which supports the diagnosis without proving the mechanism. Rule: the launch path (`Tweak.xm`, `Shared/OITIPreferences.xm`, `Shared/OITIState.xm`, `Safety/OITISafety.xm` and the project headers they import) calls no `UIScreen`, `UIDevice`, `UIApplication`, `UIWindow` or `UIView` class methods. Do screen-dependent work in a hook, a layout pass or a `dispatch_after` block. `tools/check_ctor_path.py` enforces it. The position helpers are split for this reason: `OITIPositionValues.h` (Foundation only, launch path) and `OITIPositionLimits.h` (UIKit, hooks and Settings only).
- **The loop guard cannot see a crash inside `preferencesChanged()` (Nov 2026).** It records a launch in `OITIEvaluateLoopGuard`, which runs after `preferencesChanged()` in the %ctor. A crash before that point leaves no trace in `OITIBootLog.plist`, so safe mode never trips and the loop continues until the tweak is disabled from outside (Dopamine's Tweak Injection switch). Not changed; see the proposal in `OVERVIEW.md`.
- **A real compile check exists off-device (Nov 2026).** Theos (`vendor/logos`) plus clang 18 and the Theos iPhoneOS16.5 SDK can Logos-preprocess every `.xm` and syntax-compile it as plain Objective-C for `arm64-apple-ios16.0` (no C++, no modules, no link). It catches compile errors and unknown selectors; it does not catch runtime behavior such as the bootloop above.

- **The loop guard runs in two steps, before the preferences reload (Nov 2026, batch 2).** `OITIGuardBeginLaunch` records the launch and `OITIEvaluateLoopGuard` decides; both run before `preferencesChanged()` (see the %ctor), and a tripped guard skips `preferencesChanged()` in favour of `OITIApplySafeModePreferences`. Anything the %ctor does before the guard is outside its protection, so keep that to the log, the early settings and the guard. `tools/check_ctor_path.py` checks the order.
- **A running Detailed download is not a notification (Nov 2026, batch 2).** The presenter evicts and replaces only non-download items when a notice or the Hello arrives, and the tracker keeps the stacked card's text current. Before this, a notification (stacking off) or a full stack removed the download element and `OITIDownloadItemRemoved` kept it away for the rest of that download. Swipes and system dismissals still count as the user's choice and keep it away.
- **A switched-off feature must say so where the user looks (Nov 2026, batch 2).** The promotion guard used to switch element creation off with only a log line. It now writes `OITIElementsOff.plist`, shown as a Settings banner until the next launch; the tweak, not Settings, owns the file's lifetime.

## Island internals (iOS 16.7, spoofed 2556)

- **The Island window is a scaled canvas.** `SBSystemApertureWindow` is 360 x 640 with Apple's own 1.15 transform (screen width / canvas width), even with every OITI setting off. Setting your own transform replaces Apple's, so an absolute scale of 1.0 is not Apple's size (it is 15% smaller on the 8 Plus). Compute any "relative to stock" factor as screen width / window bounds width.
- **Relative scale and Apple Mode (Oct 2026, tested on-device).** The X/Y scale sliders now apply Apple's canvas scale (shorter screen side / shorter window bounds side) times the slider, with new keys `RelativeScaleX/Y`; the position divisor uses the slider alone so 1.0 changes nothing. Apple Mode is implemented as one override block in `preferencesChanged` that forces the customization flags off after the stored values are read and before the old/new transition checks run, so turning it on behaves exactly like switching each feature off and the stored settings are never edited. Device-adaptation settings (Status Bar Layout; since 0.3.0 also the custom Island and banner positions, which replaced the Fix switches) are deliberately not customizations and stay as the user set them.
- **Size comes from `SBUISystemApertureLayoutMetrics`, and `sensorRegionSize` is the root.** `_inertSize`, `minimumCompactSize`, the compact padding areas and the corner radius all derive from it. Scaling only its return value shrinks the pill while icons, artwork and text keep stock size. Hooking `_inertSize` alone changes derived numbers but no pill size. Apple re-reads the getter on every layout, so a relayout request makes changes live.
- **A window transform scales content too**, so it cannot shrink only the pill. Compact pill width = sensor region + content outsets; compact height is constant.
- **Content is hosted, not drawn in place.** Element content sits in `_SAUIProvidedViewContainerView` > `_SAUIPortalView` (CAPortal). Idle has no element view controller at all.
- **Element model to build on:** `SBSystemApertureProvidedContentElement` + `SBUISystemApertureCustomContentProvider`, registered through `SAUISystemApertureManager`, ordered by `SBSystemApertureElementAuthority`. `SBChargingSystemApertureElementProvider` is a working SpringBoard-side example.
- **Dump workflow.** Put the phone in a state, run `dumpstate <label>`, upload the log. Dump class lists in small batches (5 classes) so the logger's backlog limit does not drop lines.

## Island elements (iOS 16.7, observed building Island Notifications)

- **Register through `SBSystemApertureController -registerElement:`.** It is the registrar SpringBoard's own providers use (it is also the element registrar of `SBSystemAperturePresentableManager`). The registration is a `SAUIElementAssertion`; `invalidateWithReason:layoutModeChangeReason:` removes the element. Capture the controller from its `-initWithWindowScene:` and its first `-registerElement:`. Calling `SAUISystemApertureManager registerElement:` directly appears to work but leaves the element without a host.
- **Apple classifies every element.** The manager asks `respondsToSelector:` for `hasIndicatorBehavior`, `hasAlertBehavior` and `hasActivityBehavior`. A bare `SBSystemApertureProvidedContentElement` answers none, so `-[SAUISystemApertureManager _elementViewControllerForElement:creatingIfNecessary:]` returns nil without ever calling `SAUIElementViewController initWithElementViewProvider:`, and `_reevaluatePromotedElements` then throws on `-[NSArray insertObject:atIndex:]` (object cannot be nil). **That uncaught exception aborts SpringBoard** and loops it. OITI's element is a runtime subclass (`objc_allocateClassPair`) that answers `hasAlertBehavior` YES, the other two NO, and `preferredAlertingDuration:` (like the charging alert).
- **The "identifier" of `initWithIdentifier:contentProvider:` is an object, not a string.** Real elements pass their own provider (`SBLockElementViewProvider`, `SBChargingSystemApertureElementProvider`). It must answer `elementIdentifier` and `clientIdentifier` (`com.apple.springboard` for SpringBoard-owned elements). An `NSString` throws `-[__NSCFString elementIdentifier]: unrecognized selector`; a small stub that answers those two (and logs anything else it is asked) works.
- **Content structure.** `SBUISystemApertureContentProvider` is the container (setters for leading, trailing, minimal, primary, secondary and action content view providers). Each holds a wrapper with `providedView`: `SBUISystemApertureCustomContentProvider initWithView:`. Using the wrapper as the element's whole content provider leaves every view nil.
- **Layout modes (min / max / preferred).** Observed: lock 1/1/1, status bar pill 1/2/2, in-call scene 1/3/2, charging -1/2/2. An element with 1/3/3 reports `layoutMode=3` and shows the expanded layout (icon, title, message, about 337 x 82 in window units, 98 high for a longer message). 1 is compact and 3 is expanded (both confirmed on screen); 2 is the wide pill (unverified). In compact the icon showed but the trailing text did not; not understood yet.
- **Where it lands.** After registration `elementHost` and `layoutHost` are `SAUIElementViewController`; views sit in `SAUIElementView` inside `_SBSystemApertureContainerViewContentView`. The rounded shape comes from three ancestors (`_SBSystemApertureContainerViewContentView`, a clip view with `masksToBounds`, `SBSystemApertureContainerView`), all with the same radius.
- **Banner pipeline.** On 16.7.16 each banner arrives at `-[SBNotificationBannerDestination postNotificationRequest:]` (`v24@0:8@16`; the 2023 trace that suggested `postNotificationRequest:forCoalescedNotification:` is not this version). The request is an `NCNotificationRequest` (`content.header`, `.title`, `.subtitle`, `.message`, `sectionIdentifier`). Hiding the stock banner by fading `SBBannerWindow` until the destination's `presentedBanner` is nil leaves Notification Center, the lock screen list and Focus filtering intact; swallowing the dispatcher call (as some tweaks do) breaks them.
- **A tap should run the stock banner's own action.** While OITI's element shows, the stock banner is only faded: `BNContentViewController > SBNotificationPresentableViewController > NCNotificationShortLookViewController` are still in `SBBannerWindow`. `NCNotificationViewController -_executeDefaultAction:` (`v20@0:8B16`) runs what a tap on it runs, so Apple's own code opens the right conversation and dismisses the banner. The `NCNotificationRequest`'s `defaultAction` is nil on 16.7.16, so a URL-based approach finds nothing. Match the banner to the element by the request (`notificationRequest`). Fall back to the app launch when the banner is gone.
- **Gestures on the Island window.** Recognizers on the element's `SAUIElementView` and on `SBSystemApertureWindow` both receive touches (`cancelsTouchesInView = NO`, permissive delegate); the window one is the one that fired in testing. Make the window ones accept only touches that start inside the element, and guard against handling a gesture twice.
- **Hook by name pattern with an encoding check.** Find the method with `class_copyMethodList`, require the exact type encoding, install with `class_replaceMethod` and `imp_implementationWithBlock`, always call the original first, and log candidates when nothing matches. A wrong guess about a private ABI then costs a log line instead of a crash.
- **Crash recovery across launches (Oct 2026, tested on-device).** Nothing about an expanded Island survives a SpringBoard restart, so "recovering the expanded state" was the wrong target. The loop risk is a re-delivered notification rebuilding the element that crashed. A breadcrumb file written synchronously just before the element is registered (the only risky call) and deleted when the last element leaves lets the next launch open a short window with elements off, using the stock banner. Presenting returns NO there, and callers already only fade the stock banner when an element really went up, so a suppressed notice is never swallowed. A respring requested from OITI's settings is recognised by the loop guard's intent marker and does not open the window.
- **Download progress as an ordinary element (Oct 2026, tested on-device).** The progress element is a `OITIPresentNoticeElement` variant like the Hello: same icon/headline/body structure, its own body (`OITIProgressBarView` plus one monospaced-digit text line, fixed 260 pt width so text changes never re-lay out the element), a very long `timeoutDuration`, and a flag on the item. Everything shared (breadcrumb, recovery window, stack, swipe dismissal, Apple Mode gating) comes for free. The tracker is separate from the element: sources only push bytes, speed is smoothed from byte deltas (EWMA 0.7/0.3 at least 0.25 s apart), and the element is presented, updated, limited and ended from one `OITIDownloadsRefresh`. Removals the tracker did not cause (swipe, a notice replacing it, capacity) mark the session collapsed so it does not fight the user; a new download clears that. Retries when presenting fails are spaced 10 s so a recovery window does not log every tick.
- **Apple's alert timer ends an OITI element on its own (Oct 2026, found with the download bar).** `OITINotificationElement.preferredAlertingDuration:` is read by the system, which ends the element's alert after that many seconds without telling OITI. It used to answer the notice duration for every element, which was invisible for notices (OITI's own timeout fires at the same moment) but removed a long-lived element after about 5 s and left OITI's own state (`sDownloadItem`) pointing at nothing. Two rules came out of it: answer that timer per element (`OITIItemForElement`), and never trust that an item in OITI's list is still on screen; a long-lived element should check that its views still have a window and recover with a back-off when they do not. The same applies to anything future that lives longer than a notice.
- **The alert timer also applied to the Hello (Nov 2026, found by reading the code, not observed on the phone).** `preferredAlertingDuration:` answered the notice duration (default 4 s) for the six-second Hello too, so by the rule above Apple's timer could end it before the clip does. It now answers the Hello item's own timeout (clip + last-frame hold + 2 s). Rule: every element kind that lives longer than a notice needs its own answer there. The Hello was also an activity, not an alert, when the notification style was Compact (only the download was exempt from the style); it is now treated like the download. Unverified on the device at Compact.
- **Holding the last frame of the Hello is a delay, not an encode (Nov 2026).** An `AVPlayer` with the default end action keeps showing the last frame after the end notification (standard AVFoundation behavior; on the phone this is what the 0.5 s hold relies on, and it is not yet checked there), and the clip's last frame is pure black, so the hold is an empty black card (0.5 s was judged too long on the phone; it is 0.25 s from build `OITI-exp-2026-11-03-b`). Holding the fully drawn word instead would need a re-encode of `StartupHello.mp4` (a freeze inserted around 4.3 s); that was not chosen.
- **Opening Insula's own Settings page (Nov 2026, verified by the owner on the phone with `uiopen`).** `prefs:root=Insula` lands on Insula's page: the value after `root=` is the `label` of the PreferenceLoader entry (`OITIPrefs/Resources/entry.plist`), so renaming the display name means changing `OITIOpenInsulaSettings()` as well. SpringBoard opens it with the same `openURL:options:completionHandler:` call the notification tap fallback already uses; the completion handler is nil, so OITI cannot tell whether the page was found. The Hello has its own tap action because it has no request and no stock banner: through the shared notification path its tap used to fall to launching the Settings app, and the sole-banner fallback (no request, exactly one stock banner on screen) could have run an unrelated banner's action.
- **The Detailed look's completion check sits in the trailing slot (Nov 2026, unverified on the phone).** The Detailed element is Apple's expanded layout with OITI's own views: a leading icon, a headline, a trailing label (the percentage) and a body of a bar plus one text line. Changing the body's height at completion would change the element's layout, so the check is a 16 pt badge added as a subview of the trailing label, whose text colour is cleared (text and size kept). If the slot clips or misplaces the badge, the first thing to look at is its frame in the log line `Detailed look: completion check shown in the trailing slot`.
- **The percentage return-to-idle limit counts progress, not time (Nov 2026).** `DownloadIdleAfterPercent` (1 to 99) compares the snapshot's fraction (the value the bar shows; the mean with several downloads) with the limit on every tracker tick, so a download that is already past it when its bar would first appear never shows the bar. 100 is not offered because completion is its own state (`OITIDownloadEnd`).
- **Why the in-card stack could not give each notice its own tap (Nov 2026, read in the code; that look was removed in build `OITI-exp-2026-11-03-d`).** Each notice is a registered element, but only the newest is on screen; the older ones were compact cards built into the newest element's secondary content (`OITIRefreshNewestNoticeComposite`) and carried no recognizers, so a tap on them reached only the newest item's `OITINoticeActions`. The separate cards (tested by the owner from build `OITI-exp-2026-11-03-c`, now the only look) draw the older notices in an OITI window under the Island, each with its own recognizers and its own actions object (held by the card, because recognizers hold their target weakly). A card's swipe removes the notice on the next run loop pass, because the removal rebuilds the cards and would otherwise free the card and its actions object inside the recognizer's own callback.
- **Opening the exact older notification is still open (Nov 2026).** The owner confirmed that tapping a card opens the app the notice came from and expects a real notification to open that notification itself. The tap path is the stock banner's own default action while that banner is alive, then the default action's URL, then launching the app, so for an older notice (whose banner is probably gone) it may only open the app. This is unverified with a real notification; if it only opens the app, the next step is a dump of what the stored `NCNotificationRequest` offers (its default action and any URL or bundle user-info), not a guess.
- **Where the cards go is measured, not computed (Nov 2026, unverified).** The cards use the screen rectangle of the Island's `SBSystemApertureContainerView` (conversion includes OITI's own position and scale transforms) and wait until it has stood still 0.15 s, because the model value of a view that is animating may already be its end value. Before this round only the top and centre of an expanded Island had been used (`OITIIslandPillRect` throws the height away when it is 80 pt or more), so the bottom edge of the expanded card had never been measured. If the cards sit wrong, the level 2 `STACKCARDS island rectangle probe` lines show every candidate rectangle and which one was chosen (the one reaching lowest on screen).
- **Card motion is a transform offset, and places are kept current (Nov 2026, batch 6, build `OITI-exp-2026-11-05-a`, unverified on the device).** The stack cards keep one view per stack item (identity of the item dictionary) and move with a transform that animates back to identity, because the 30 Hz tick owns the card's `bounds` and `center` (setting `frame` under a transform is undefined, and an animation on the center would fight the tick). A glide starts from "drawn where it was" = the card's running offset (`presentationLayer.affineTransform.ty`) plus the slot difference times the step, set without animation, then animated to identity; that is only right if the new place is already set, so the tick now sets places whenever the Island rectangle is found, not only when the cards are visible. A leaving card is not in the card list any more (the tick ignores it), is sent behind the others and finishes by removing itself; its completion also runs when an animation is cut short, so the removal is idempotent. UIView animations use model values for hit testing, so a card that is still sliding takes touches at its final place. Open (device): whether a new notification closes the Island-rectangle gate (the new element is not on screen yet) and so turns the arrival into a group fade; the `STACKCARDS` lines show it.
- **The morph copy is a second card view in the window, not the real card (Nov 2026, batch 7, unverified on the device).** The real card lives in the root view, whose alpha is the gate (0 while the new notice is not on screen yet), so it cannot be seen travelling. The copy is a subview of the window with the same item (same layout), animates `frame` and `layer.cornerRadius` in one spring block with `layoutIfNeeded` inside it (so the content re-lays out and moves with it), takes no touches and is removed 0.26 s after the real card shows (the root's 0.22 s fade-in must be finished, otherwise the product of the two alphas dips) or 1.6 s after it started, whichever comes first. The Island's rectangle for the start is read at the moment the new notice is added: `OITIPresentNoticeElement` calls `OITIStackCardsRefresh` after adding the item and before registering the element, so the Island still shows the previous notice. A notice younger than 0.8 s has not settled in the Island, so no copy is made for it (a burst).
- **A running App Store install has an "installing" phase: installPhase 1 (Nov 2026, batch 8, from device logs).** Three installs on the 8 Plus (iOS 16.7.16): installPhase 3 (state 5) at the start, 0 (state 1, `progressState` 3 to 4) while downloading, then **1 (state 1, `progressState` 5)** with the fraction still moving (TikTok 0.60 to 0.96 over 30 s; War Thunder Mobile stayed at 0.76 for the 10 s it lasted), and finally the placeholder leaves the list with the app installed. Paused is installPhase 0 with state 2, `progressState` 2 and `isPaused` YES; a cancel is 0 with state 4 and then the placeholder leaves with the app not installed. An App Store update of an installed app (TestFlight) is a placeholder like an install (0 with state 5, then 1). The switch to phase 1 happens at different percentages (60 to 96), so the percentage cannot be used to tell downloading from installing, the phase can. TestFlight installs from a build were not tested (no developer code).

## Source layout and the module split (v0.3.0)

- Quoted imports in OITI are written relative to the OITI folder (`#import "Shared/OITIShared.h"`) and `OITI_CFLAGS` has `-I.`. Do not use `../` paths: Theos compiles the Logos output, and a relative path from the generated file does not point where the source file sits. The existing `#import "OITIDeviceProfiles.h"` worked for the same reason (the project folder is on the include path).
- A `static` global or function cannot be shared between `.xm` files. Moving code into its own file means dropping `static` on what other files use and declaring it once in a header (`extern` for variables; for a `const` variable in Objective-C++ the definition needs `extern` too, because `const` alone gives internal linkage).
- A Logos `%group` can only be initialised (`%init(Group)`) in the file that defines it. To move a group into its own file, add a plain function in that file that calls `%init(Group)` and call that function from `%ctor`. This is how `OITIHooks` moved (`OITIInstallIslandSizeHooks` in `IslandSize/OITIIslandHooks.xm`); Logos generates no constructor of its own for a file that only has explicit groups.
- A `static const` constant that two files need goes into a header as `static const` (each file gets its own copy, which is fine for a constant); a variable needs `extern` in the header and one definition. A class that several files use gets its `@interface` in a header and its `@implementation` in one file.
- When two modules are interleaved, the state both touch stays with the code that owns the lifecycle. The Detailed download element is built by the notification presenter, so `sDownloadItem` and its two companions stay with the presenter and the download module declares them `extern`; they moved in the IslandNotifications round.
- A shared constant that is not a plain number (`NSString * const`, `NSTimeInterval`) is `extern const` in a header and defined without `static` in the file that owns it, after that file has imported the header (in Objective-C++ a `const` without a prior `extern` declaration has internal linkage and the other files fail to link).
- When a module is pulled out of code that another module already calls, the other module's header is where the new header gets imported (`OITIIslandNotifications.h` imports `Startup/OITIStartup.h`), so the files that use the symbols keep compiling without each adding an import. A header that two modules include needs `#import` (which does not double-include), not `#include`.
- State that the `%ctor` and a module both touch (the guard's state-file paths, the guard settings the preferences reload writes) is defined in the module that owns it and declared `extern` in that module's header; the `%ctor` imports the header. Settings that every module reads are defined once in `Shared/OITIState.xm`. A `static` variable with a single user (`sLastPrefSnapshot`) moves with that user and stays `static`.
- Helpers that more than one module calls (the exception-safe getters and the instance-variable readers of the install dump) live in `Shared/OITIRuntimeHelpers.xm`, declared once in `Shared/OITIShared.h`. A module header declares only what its own module defines.
- Every source file has to be in `OITI_FILES`; a file left out compiles nothing and fails only at link time.
- There is no compiler in the chat, so a split is verified with `tools/check_split.py` (`COMMANDS.md`, section 19): it compares the code-only lines of the old and new files, checks that every identifier a new file uses is defined in it or declared in an included header, and optionally runs Logos (github.com/theos/logos) over every file. Selectors sent to a `Class` or `id` also need a visible `@interface`, or the build fails under ARC; that is why Apple's private class declarations live in `Shared/OITIApplePrivate.h`.

## Build, packaging and tooling pitfalls

- **Theos picks up headers from `$THEOS/include` before your project's.** A stale installed copy shadows your edit. Import the module's own header with quotes (`#import "OITLog.h"`) inside that module, and rebuild OITCore first so the install step refreshes the copy.
- **Macro parameters must not match selector keywords.** A parameter named `tag` also replaced the `tag:` part of `-logLevel:tag:format:` and produced "expected ']'" errors. Name parameters `tag_`, `level_`, and so on.
- **`-Werror` makes warnings fatal.** A header with any nullability annotation needs `NS_ASSUME_NONNULL_BEGIN` before every pointer in it; mixed-type `?:` operands need an `(id)` cast.
- **Arch builds warn "incompatible arm64e ABI compiler".** Harmless for arm64 devices; do not publish packages built there.
- **Package versions:** dpkg sorts `0.0.10` below `0.1.0`. The `-N` build counter is per machine, so "downgrading" warnings between machines are harmless. Release builds use `FINALPACKAGE=1`; clear `packages/` first (it keeps every earlier build) and ship OITCore with OITI because OITI depends on it.
- **The phone's `defaults` has no `delete` mode.** Write an explicit value (`-int 0`) instead.
- **`sbreload` can drop the SSH session.** Log in again and re-define shell helpers such as `dumpstate`.
- **`iphoneos-arm64` is only the rootless package label.** The binaries inside are fat arm64 + arm64e. Check a release by downloading it, then `ar x`, extracting `data.tar.*` and reading the Mach-O header. A package without `FINALPACKAGE=1` is versioned `X.Y.Z-N+debug`; do not ship one as a release.

## Git and release lessons

- **GitHub rejects account passwords for git.** Use `gh auth login` and `gh auth setup-git`.
- **Squash merge means the old branch is not an ancestor of `main`.** Delete it with `git branch -D` only after the PR shows as merged. Repo settings now squash-only with auto-delete, so `experiments` disappears after each merge.
- **Merge only after on-device tests.** PR #3 was merged a minute after the push and put untested code on `main`. The checklist in `WORKFLOW.md` exists for this reason.
- **Do not paste commands with inline `#` comments** into the phone shell or the Mac's zsh.
- **Look-alike GitHub repos exist.** A repo that copies a real tweak's files but has a README advertising a Windows `.exe` or a `.zip` download, unrelated topics, one star and no contributors is a malware pattern. Check the author, stars, forks and contributors, do not open the download, and prefer reading source over installing packages from unfamiliar repos. OITI's own code is written from scratch; other tweaks were used only as references for what is possible.
- **Pre-releases use a tilde and a tag with a dash.** `OITI/control` says `0.2.0~beta.1` (sorts below `0.2.0`), the tag is `v0.2.0-beta.1`, and the GitHub Release is marked pre-release.

## Working with Claude across chats

- Hand over the docs (`OVERVIEW.md`, `LEARNINGS.md`, `IDEAS.md`, `DIAGNOSTICS.md`, `COMMANDS.md`, `WORKFLOW.md`) rather than re-uploading source, and upload only the specific files a task needs. Long chats use a lot of usage; start a new one when a chat gets bloated.
- Claude cannot run git on your machines. It can clone the public repo in its own sandbox to read code, but GitHub web pages, `/tree/` pages and the API are unreliable (rate limits). Paste terminal output as text and upload large logs as files.
- Prefer small, staged tasks with one complete deliverable each. Deliveries are full files in a `.tar.gz` with repo-relative paths (extract with `tar -xzf` on `experiments`).
- Ask for exact copy-paste commands; add new commands to `COMMANDS.md`.
- **Remote testers:** a log from their phone beats theory. Ship one build with a read-only log and an opt-in fix, and put the choice in a settings picker so the tester does not need a terminal. Ask for one command at the end. Tell them to wait 2 minutes between resprings (safe mode).
- **A tester's first symptom can be a safe-mode side effect.** Check `grep -e SESSION -e SAFE` first: safe mode silently disables every hook while the spoof stays on.

## Ways of working

- Reason about consequences before editing code; avoid speculative iteration.
- Prefer full-file rewrites over patch-style diffs.
- Split large changes into stages, each a complete, buildable file.
- Revert to the last known-good state when a change produces a crash loop, then investigate before re-attempting.
- Capture evidence before changing code: a log or dump from the exact moment of the symptom beats a plausible theory.
- Mark untested work clearly and keep it on a branch until it has run on-device.
